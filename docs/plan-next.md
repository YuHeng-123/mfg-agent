# 项目下一阶段计划（v2 · 项目导向）

> 上一版把一半篇幅放在简历和演示话术上，跑偏了。这一版只谈工程。
> 结论先给：**功能封板，但质量没封板——Recall@1 只有 68%，这是当前最大的一块短板。**

---

## 一、当前基线与短板

| 指标 | 现在 | 评价 |
|---|---|---|
| Recall@1 | 68.0% | **短板**。三分之一的问题，top1 不是正确段落 |
| Recall@5 | 94.0% | 可以。说明东西在候选里，是排序问题不是召回问题 |
| MRR | 0.823 | 同上，排名结构有优化空间 |
| 引用精确率 | 62.7% / 62.8% | 中等。多引了相邻但不完全对应的段落 |
| 差距召回/精确 | 100% / 100% | 规则题，已到位 |
| 单次提问耗时 | 1.9 s（首次含索引构建） | 冷启动明显，热态约 100ms |
| 测试 | 60 条 | 覆盖到闸和接口，缺检索质量回归 |

**关键判断：Recall@5 94% 而 Recall@1 68%，说明问题不在"找不到"，在"排不对"。** 这类问题有明确的工程手段，不是玄学。

## 二、五个阶段

### P1 · 错误分析（诊断，不改代码，约 1 小时）

先把 8 个 Recall@1 失败的样本逐个打开，归因到具体机制。

| 任务 | 产出 |
|---|---|
| 1.1 导出每题的 top3 与 gold，标注差距 | `docs/error-analysis.md` |
| 1.2 给每个失败样本归因，归到五类之一：分词问题 / 同义词缺失 / 章节权重 / 多跳（需要跨段）/ 标注问题 | 同上，附占比 |
| 1.3 标注问题单独拎出来——如果 gold 标错了，先改标注再谈优化 | 改标注的清单 |

**验收**：每个失败样本都有归因，且五类加起来等于 8。写不出归因的，说明检索逻辑还没吃透。

> 这一步的价值：不做它就去调参数，等于闭眼改代码。而且"我第一次跑 68%，看了 8 个失败样本，发现 3 个是同义词问题"这句话，比"我调到了 85%"有说服力得多。

---

### P2 · 检索质量（按 P1 的归因逐项改，每步记录 before/after，约 4 小时）

按预期收益排序，做一步测一步，**不打包提交**：

| 改动 | 手段 | 预期 |
|---|---|---|
| 术语归一 | 领域词典：气蚀/汽蚀/抽空、密封/盘根、联锁/保护、滤芯/滤清器 | 同义问题 |
| 查询扩展 | 用词典把查询词扩成同义组，扩出来的词降权 0.5 | 同上 |
| 章节权重重标定 | 现在 section×1.8 / title×1.5 是拍的，用 grid search 在训练集上标，**在测试集上验** | 排序问题 |
| 章节号加权 | 问题里出现 `E05`/`7.1.6` 时，标题含该编号的段落额外 ×2 | 精确命中 |
| 停用词与虚词 | "怎么/多少/需要/一下"这类词不进索引 | 降噪 |

**验收**：
- 每一步都跑完整评测，记录 `Recall@1` 变化，写进 `docs/retrieval-tuning.md`（表格：改动 → @1 → @5 → 说明）
- **训练/测试切分**：样本分 70/30，调参只看训练集，最终数字报测试集。不切片就是在测试集上调参，数字会虚
- 如果某项改动没涨，照样记录，并写"为什么没涨"

> 这条最容易翻车：调参调到测试集上，数字好看但没意义。所以先切分，再动手。

---

### P3 · 多跳与引用覆盖（补一类真实难点，约 3 小时）

现在的样本基本是单段命中。真实的运维问题往往要跨段：E05 的处置步骤在 5.3，阈值在 3.1，维护周期在 6.1。

| 任务 | 产出 |
|---|---|
| 3.1 新增 20 条多跳样本（gold 是 2-3 个段落，分布在不同章节/不同页） | `evals/equipment.jsonl` 扩到 52 条 |
| 3.2 新增指标：**引用覆盖率**（gold 集合里被引用到的比例），与引用精确率一起看 | `core/evals/metrics.py` + 报告新增一列 |
| 3.3 让 stub 的结论选取支持多段拼装（现在的 60% 分数裁剪对多跳是致命的） | 代码改动 + 回归测试 |

**验收**：报告里出现"单跳 Recall@1 / 多跳引用覆盖率"两个数，且多跳那一栏明显低于单跳——**低是对的，说明这类题真难**。

### P4 · 写操作闭环（把草稿变成流程，约 3 小时）

现在工单和差距只写到 JSONL，没有状态，没有查询，前端看不到历史。

| 任务 | 产出 |
|---|---|
| 4.1 换 SQLite，三态状态机：`draft → confirmed → closed` | `core/store/` 或各域 store |
| 4.2 `GET /api/tickets`、`POST /api/tickets/{id}/confirm`、差距清单同理 | 接口 + 测试 |
| 4.3 前端底部草稿条改成"最近 5 条"列表，可展开看状态 | 页面改动 |

**验收**：一条工单能从生成 → 确认 → 查询列表里看到，且**未经确认的不出现在正式列表**（这条要有测试）。

## 四、明确的取舍

**做：**
- 错误分析驱动优化（不是拍脑袋调参）
- 训练/测试切分（否则数字是假的）
- 多跳样本（真实难点，且能暴露现在的短板）
- 写操作闭环（补完整度，成本低）

**不做：**
- 扩语料到 8 本手册。会让所有指标掉一截、全部报告作废重跑，36 小时不够消化。**这是下一轮的事，写进 TODO**
- 向量检索上线。离线拉不到模型；用规则+词典能覆盖的部分先覆盖，剩下的诚实标"未启用"
- 真 LLM。没 key，且它会掩盖检索问题——模型强了，检索烂也能答对，反而测不出
- 第三个领域、Docker、前端美化

## 六、实际产出（与计划的偏差）

计划之外多做的：

- **子句检索的作用域继承**。为了让多跳能答，按标点切开分别检索，结果子句里没有型号，
  等于把型号过滤关掉了——跨型号引用从 0 涨到 23.2%。发现后改为子句继承首轮解析出的实体作用域。
  这个坑在原计划里没有，是做 P3 时才暴露的。
- **章节多样性选择**实测完全无差别（输出与"直接取 top3"一致），删掉了，没留一个永不生效的开关。

计划里没做的：

- 语料扩到 8 本手册（会让全部报告作废重跑，刻意留到下一轮，已写进 README）
- 真 LLM 对照（无 key）
