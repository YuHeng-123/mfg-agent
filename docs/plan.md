# 设备运维 Agent（制造业版）—— 项目方案

> 一句话：把「设备手册 + 故障工单」做成一个能查、能引用、能建单的运维助手。
> 定位：**制造业 AI 应用岗的敲门砖**，不是通用聊天机器人。

---

## 一、为什么做这个

### 对接的岗位关键词

| JD 常见要求 | 这个项目怎么对 |
|---|---|
| 大模型应用落地、RAG 知识库 | 手册检索 + 页码引用 |
| 工业知识库、设备文档问答 | 按设备型号过滤的混合检索 |
| 工单 / 售后 / 运维流程 | 故障分类 → 建单 → 升级闭环 |
| AI 应用安全、可控 | 涉电/拆机强制转人工 + 无引用降级 |
| Python / FastAPI / Agent 开发 | 复用已有 Agent 运行时与 MCP 工具层 |

### 不做什么（防跑偏）

- ❌ 不做工业视觉、不做 PLC/工控对接（不是你的能力圈，硬蹭会被问穿）
- ❌ 不做预测性维护（需要真实时序数据，做出来是假的）
- ❌ 不做前端炫技（一个极简页面够用，重心在检索质量与可解释性）

## 二、三个核心场景

### 场景 1：故障问答（带出处）

> 工人：「3 号线空压机报 E05，怎么处理？」

系统：先识别设备型号 → 检索该型号手册的相关章节 → 回答步骤 → **每条结论附「手册名 + 页码 + 原文片段」** → 如果涉及涉电/拆机，直接转人工。

**为什么这是核心**：工业现场最怕 AI 瞎答。有出处，工人才敢照做。

### 场景 2：自动建单

> 对话里识别出「这是个需要上门的故障」→ 自动生成工单草稿（设备型号、故障现象、初判等级、SLA），人工确认后入库。

**为什么重要**：制造业要的不是「能聊天」，是「能进流程」。

### 场景 3：历史故障复用

> 「同型号设备上次类似故障怎么处理的？」

检索历史工单 → 给出上次的处理方案和耗时 → 附工单号可追溯。

## 三、技术架构

```
┌─────────────────────────────────────────────┐
│  web/ (极简前端：对话 + 工单看板)              │
└──────────────────┬──────────────────────────┘
                   │ FastAPI (SSE 流式)
┌──────────────────▼──────────────────────────┐
│  agent/  Agent 运行时（复用现有）              │
│   ReAct 规划 → 并行工具调用 → 自纠错 → 双熔断  │
│   工具：查手册 / 查设备档案 / 查历史工单 / 建单 │
└───────┬──────────────────────┬──────────────┘
        │                      │
┌───────▼─────────┐   ┌────────▼─────────────┐
│ guard/ 安全护栏   │   │ ticket/ 工单系统      │
│ 涉电拆机→转人工   │   │ 分类/建单/升级/SLA    │
│ 无引用→降级      │   └──────────────────────┘
└───────┬─────────┘
        │
┌───────▼─────────────────────────────────────┐
│  rag/  检索层                                │
│  切分(按章节/表格) → 向量化 → 混合检索        │
│  = 向量 + BM25 + **设备型号硬过滤** → 重排    │
└─────────────────────────────────────────────┘
```

### 三个关键设计决策（面试就讲这三点）

1. **型号硬过滤**：查「3 号线空压机」时，先锁定型号，只在该型号手册里检索。
   不做这层，会把 A 型号的维修步骤套到 B 型号上 —— 这是工业场景最容易出事的地方。

2. **答案必须带引用**：`citation.py` 校验每条结论是否有 `(手册, 页码, chunk_id)`；
   没有引用的结论直接标记为「低置信，建议人工确认」。

3. **安全边界前置**：`safety.py` 用关键词 + 规则先扫一遍（高压/带电/拆机/燃气/高温），
   命中就跳过 LLM 直接回「该问题必须由持证人员处理，已为你创建工单」。

## 四、MVP 范围与验收标准

### 必须有的（第一版）

- [ ] 灌入 **2-3 本真实设备手册**（PDF），能按章节切分并入库
- [ ] 检索：向量 + BM25 + 型号过滤，返回 top-5 带页码
- [ ] 问答：LLM 基于检索结果回答，**每个结论带出处**
- [ ] 安全护栏：命中高危词直接转人工
- [ ] 工单：能建单（写 JSON/SQLite）并在 CLI 里查看
- [ ] 评测脚本：跑出 **Recall@5** 和 **引用准确率**

### 验收标准（量化，写进 README）

| 指标 | 目标 |
|---|---|
| Recall@5（20 条人工标注问题） | ≥ 0.85 |
| 引用准确率（引用的页码确实含该内容） | ≥ 0.90 |
| 高危问题转人工率 | 100%（不漏） |
| 单次问答耗时 | < 8 秒 |

> 这些数必须自己跑出来再写，不能凭空填。

### 第一版不做

- 多设备档案管理、权限、Docker 编排、前端美化

## 六、数据来源（必须真实）

| 类型 | 来源建议 |
|---|---|
| 设备手册 | 开源硬件文档、公开的工业设备说明书（阿特拉斯空压机、西门子/施耐德公开手册、树莓派类工控文档） |
| 故障样本 | 从手册的「故障代码表」反向构造 20 条问答，人工标注正确页码 |
| 历史工单 | 自己按手册场景造 10 条 JSONL（标注为「模拟数据」，面试时说明） |

> ⚠️ 手册必须真实存在，评测集必须人工标注。造假的评测数据面试现场一跑就穿。

## 七、评测方法

```
scripts/eval_retrieval.py
  输入：data/eval/questions.jsonl（20 条：问题 + 正确 chunk_id）
  输出：Recall@5 / MRR / 平均耗时
```

`data/eval/questions.jsonl` 格式：
```json
{"q": "AX300 报 E05 怎么处理", "gold_chunk_ids": ["ACME-AX300_p087_c02"], "type": "fault_code"}
```

引用准确率：随机抽 20 条回答，人工核对「引用的页码里是否真有这句话」。

## 八、简历里怎么写（成品文案，数字待实测后填）

> **工业设备运维 Agent（个人项目，开源）**

> 评测：20 条人工标注问题，Recall@5 = 【实测】，引用准确率 = 【实测】，高危问题拦截率 100%。

## 十、风险

| 风险 | 应对 |
|---|---|
| 手册 PDF 是扫描件，抽不出文本 | 换一本文本版手册；或用 PaddleOCR（多装一个依赖） |
| 型号过滤后检索结果太少 | 降级为「同系列」过滤，并在回答里说明 |
| 评测集太小导致数据好看但不可信 | 至少 20 条，按故障代码/操作步骤/参数含义三类各 6-7 条 |
| 时间不够 | 砍掉场景 3（历史工单复用），保留 1 和 2 |
